# DMNC-792 — Overview Restructure: Interactive Chart Bars + Pattern-Finder + Clinical References

> **This is a planning document.** No source code, tests, or config are changed by this issue. The plan below is the only file added. It is the engineering blueprint for the three threads in DMNC-792 plus the operator inputs each thread is waiting on.

## TL;DR

DMNC-792 bundles three related-but-separable threads on the Overview/chart experience:

1. **Interactive horizontal-bar restructure** — let the chart's horizontal controls (report-type pill, zoom row, marker lane) and any "pin info" readout **overlay** the chart (Z-stacked) rather than stacking in the VStack and shrinking the chart. *Detailed layout is gated on a Figma frame from the design-workflow issue; the overlay infrastructure can be built now.*
2. **Pattern-finder tool** — tap a glucose excursion → ranked list of likely contributing events (meal absorption window, insulin onset/tail, exercise, correction bolus, heart-rate/stress proxy). A generalisation of the existing Meal Impact overlay across all event types. *Largest engineering chunk; ranking weights should be grounded in the Part 3 clinical curves.*
3. **Diabetes-course materials as design source** — ingest course handouts (ISF/ICR tables, insulin onset curves, Rule of 15, GI charts) into `docs/clinical-references/`, index them, and cross-reference existing alarm/bolus/meal-impact logic against them. *Independent of 1 & 2, but **blocked on the operator handing over the materials.***

**Recommendation: split DMNC-792 into three child issues** (one per thread) so Part 3 can ship independently of the design-blocked Parts 1 & 2. This document specs all three and flags every operator/design dependency.

## Part 1 — Interactive horizontal-bar restructure

### 1.1 What exists today (verified in code)

The Overview is a single non-scrolling `VStack(spacing: 0)` (`App/Views/OverviewView.swift`):

```
GlucoseView()                         // hero glucose
SensorLineView()                      // sensor status line
TreatmentBannerView()                 // conditional (treatmentCycleActive)
ChartReportTypeRow(...)               // ← horizontal bar #1 (report-type pill, ABOVE chart)
ChartView(...)        .frame(maxHeight: .infinity)
ChartZoomRow(...)                     // ← horizontal bar #2 (zoom/day window, BELOW chart)
// .safeAreaInset(.bottom): GlucoseStatusBar()  // INSULIN / MEAL ghost buttons
```

The horizontal controls, with their real source locations:

| Control | File | What it is | Position |
|---|---|---|---|
| **Report-type pill** | `ChartToolbar.swift` → `ChartReportTypeRow` | GLUCOSE / TIME IN RANGE / STATISTICS, drives local `@State selectedReportType` | Own band **above** chart |
| **Zoom / day-window row** | `ChartToolbar.swift` → `ChartZoomRow` | 3h/6h/12h/24h (glucose) or 7d/30d/90d/ALL (TIR/stats), dispatches `.setChartZoomLevel` / `.setStatisticsDays` | Own band **below** chart |
| **Event marker lane** | `EventMarkerLaneView.swift`, mounted in `ChartView.swift` | 60pt flag-and-chip lane; `markerLanePosition` (`.top`/`.bottom`) toggled in Settings → Glucose & Display | Inside chart scroll VStack, **top or bottom** of chart |
| **TIR/TAR/TBR bars** | `StatsComponents.swift` → `StackedTIRBar` + `TIRBreakdownRow` | Horizontal stacked bar; only in the TIME IN RANGE report | Inside `TimeInRangeReportView` |
| **Pin/selection tooltip** | `ChartReportViews.swift` → `ChartSelectionTooltip` | Tap/drag readout (smooth/raw/blood/HR) | Already overlays — `ZStack(alignment: .topLeading)` in `ChartView` |

The chart already shrinks to fit: `chartHeight(available:) = clamp(available − markerLaneHeight, minChartHeight…chartHeight)`. So every band currently in the VStack (report row, zoom row, marker lane) **consumes vertical budget that the chart would otherwise use**. That is the core of the "pushing content down" complaint.

### 1.2 "Pin info" — transcription interpretation (input A)

The issue flags that "pin info" is an unconfirmed audio transcription and lists three candidate referents. Mapping each to real code, with evidence:

| Candidate | Maps to | Evidence for | Evidence against |
|---|---|---|---|
| **(a) Tap-to-pin reading readout** | `ChartSelectionTooltip` | "pin info" reads literally as the pinned data point; this is the only thing called a "pin" | Already overlays at `.topLeading`; nothing to fix |
| **(b) Chart toolbar bands** (report pill + zoom row) | `ChartReportTypeRow` / `ChartZoomRow` | "sits at the bottom of the chart… pushing content down" matches the zoom row exactly; the related DMNC-793 is literally "fixed chart toolbar above… sticky bottom actions" | "pin info" is an odd name for a toolbar |
| **(c) Marker lane / event detail panel** | `EventMarkerLaneView` + `EntryGroupListOverlay` | Marker lane sits below the chart when `markerLanePosition == .bottom` and steals 60pt; tapping a marker opens a sheet | Detail is a sheet today, doesn't "push content down" |

**Recommendation (pending operator confirm):** treat "pin info" as **(b) + (c) combined** — *the horizontal bands that occupy their own vertical slice and thereby shrink the chart* (zoom row + marker lane), and design the work so that the **pin/selection readout and the meal/event detail also float over the chart** rather than relocating it. Because the related DMNC-793 is explicitly about a no-scroll Overview with a fixed toolbar and sticky bottom actions, the dominant intent is "stop the bars from eating chart height — let them overlay." The infrastructure below (an `OverlayBar` Z-layer) is **referent-agnostic**: it works for whichever of (a)/(b)/(c) the operator confirms.

"**Overlay** in the Z-sense or visual-sense?" → **Both.** The recommended pattern is Z-stacked (on top of the chart plot area) **and** semi-transparent (so the glucose line stays readable underneath), matching the existing `ChartSelectionTooltip` (`opacity(0.75)`, black-backed) and the IOB/exercise marks that already render translucently over the plot.

### 1.3 Proposed approach

Introduce a single **chart overlay layer** so any horizontal control can be hosted *over* the plot area instead of in the VStack:

- Wrap the chart in a `ZStack` whose base layer is `glucoseChart` at full available height, and whose overlay layers are the controls the operator wants floated (zoom row and/or marker lane and/or pin readout).
- Floated controls render with a translucent black backing (`Color.black.opacity(~0.6)`) + amber-dim hairline, consistent with `ChartSelectionTooltip` and `FlagView`.
- Keep the **report-type pill** in its own band above the chart (it's a mode switch, not chart-overlapping info) unless the Figma frame says otherwise — recommend confirming in C.
- Gate the float behind the existing `markerLanePosition`-style preference so users who prefer the stacked layout keep it. Add a new `chartControlsOverlay: Bool` (default following the Figma decision) rather than hard-replacing the current layout.

**Why an opt-in flag, not a hard replacement:** the current adaptive `chartHeight(available:)` and the no-real-white / safe-area-inset invariants (CLAUDE.md) are load-bearing. A flag lets us ship the overlay behind a toggle, validate against the Figma frame, and avoid regressing the `swiftui-vstack-overflow-sinks-safeareainset` class of bug.

### 1.4 Files touched (Part 1)

- `App/Views/OverviewView.swift` — move zoom row (and optionally marker lane) from VStack siblings into a chart overlay layer when the flag is on.
- `App/Views/Overview/ChartView.swift` — host the overlay `ZStack`; the existing `ZStack(alignment: .topLeading)` around the plot is the natural insertion point. Reuse `chartHeight(available:)` but stop subtracting `markerLaneHeight` when the lane is floated.
- `App/Views/Overview/ChartToolbar.swift` — add a compact/translucent variant of `ChartZoomRow` for overlay rendering.
- `App/Views/Overview/EventMarkerLaneView.swift` — already self-contained; add a translucent-background variant when floated.
- **State (if the toggle is adopted)** — follow the 4-file UserDefaults pattern (CLAUDE.md "Adding New State Properties"): `Library/DirectState.swift`, `App/AppState.swift`, `Library/Extensions/UserDefaults.swift`, `Library/DirectReducer.swift`, plus `Library/DirectAction.swift` for `.setChartControlsOverlay(Bool)`. Add the Settings toggle to `App/Views/Settings/GlucoseDisplayCategoryView.swift` next to the existing `markerLanePosition` picker.

### 1.5 Tests (Part 1)

- Pure layout-math unit test (Swift Testing) pinning that floated marker lane returns `chartHeight(available:) == clamp(available, …)` (no 60pt subtraction) and stacked returns the existing value.
- A `DesignTokenPinTests`-style pin on the overlay backing opacity / hairline color so the translucent treatment can't silently drift.
- No snapshot harness for the chart exists today; keep verification to the math + token pins plus manual screenshot against the Figma frame.

## Part 2 — Pattern-finder tool ("find which incident" caused an excursion)

### 2.1 Transcription interpretation (input A)

"helps us find which incident works" → **"find which incident caused this excursion"** — a cause-finder / correlator. Confidence is high; the surrounding text ("ranked list of likely contributing events", "adjacent-but-expanded version of the existing Meal Impact overlay") is unambiguous. Working name in this plan: **Pattern Finder**.

Three interaction options were posed; recommendation:

| Option | Description | Recommendation |
|---|---|---|
| **Tap-to-investigate on an excursion** | Tap a high/low segment on the chart → results panel | **Recommended for V1.** Lowest new surface area; reuses the existing chart-tap gesture; mirrors the Meal Impact tap-to-reveal users already know |
| Dedicated "why is my glucose…" tab | 5th tab | Defer. High surface cost; revisit if tap-to-investigate proves valuable |
| Passive badge per reading | Badge on each excursion | Defer. Visual noise on the DOS chart; analysis is too expensive to run per-reading |

**Span beyond meals?** → **Yes.** The whole point vs. Meal Impact is breadth: meals, bolus (meal/snack), correction bolus, basal, exercise, and a heart-rate/stress proxy. **Time-window selector?** → not needed in V1; the excursion itself defines the lookback window (see 2.3). A manual window can be a later refinement.

### 2.2 What we can reuse (verified in code)

The Meal Impact module is the foundation and most of the machinery exists:

- **Confounder/cause detection:** `App/Views/Overview/MealOverlayLogic.swift` → `detectMealConfounders(meal:insulinDeliveryValues:exerciseEntryValues:mealEntryValues:) -> MealConfounders` and `enum ConfounderType { correctionBolus, exercise, stackedMeal }`. Pattern Finder generalises this from "confounders of a meal" to "candidate causes of an excursion."
- **Impact quantification:** `Library/Content/MealImpact.swift` (`deltaMgDL`, `timeToPeakMinutes`, `baselineGlucose`, `isClean`) and `computeMealOverlayDelta(...)`. The same baseline/peak/delta math applies to any excursion window.
- **IOB onset/tail curves:** `App/Modules/IOB/IOBCalculator.swift` — `ExponentialInsulinModel.bolus(preset:)` / `.basal(diaMinutes:)` + `computeIOB(deliveries:bolusModel:basalModel:at:)`. This is the physiological model for "was insulin still active during the excursion?" — directly answers the insulin onset/tail question.
- **Event data already in state:** `mealEntryValues`, `insulinDeliveryValues` + `iobDeliveries`, `exerciseEntryValues`, `heartRateSeries` (HR proxy for stress), `sensorGlucoseValues`. All are loaded on the Overview already (used by `ChartView`).
- **Marker/event domain types:** `Library/Content/EventMarker.swift` (`EventMarker`, `EventMarkerType`, `ConsolidatedMarkerGroup`). The existing `updateMarkerGroups()` in `ChartView` already enumerates every event with a timestamp — the candidate-cause set is essentially the markers within the lookback window.
- **GRDB historical queries:** the Meal Impact plan added time-range glucose queries (`getSensorGlucoseValues(from:to:)` pattern). Reuse for excursions older than the in-memory 24h window.

### 2.3 Proposed engine design

A pure, testable **`PatternFinder`** (in `Library/Content/`, both-targets-safe, no `UIApplication`) plus a thin **`PatternFinderMiddleware`** (in `App/Modules/PatternFinder/`) that triggers computation and loads any historical data:

1. **Excursion definition.** From a tap, snap to the enclosing excursion: the contiguous glucose segment that crossed `alarmHigh` (hyper) or `alarmLow` (hypo) around the tapped time, bounded by the last in-range crossing before and the return-to-range after (cap the lookback at ~4h). Reuse `state.alarmHigh`/`alarmLow` computed accessors (day/night profile aware — CLAUDE.md). Output: `Excursion { direction: .high/.low, start, peak, end, peakDelta }`.

2. **Candidate enumeration.** Collect every event whose physiological influence window overlaps the excursion:
   - **Meals** — carb absorption window `[meal.timestamp, meal.timestamp + ~3h]` (the exact tail comes from the Part 3 GI/absorption curves).
   - **Bolus / snack bolus** — activity window from `ExponentialInsulinModel.bolus(preset:)` (peak ~55–75m, DIA 6h). A *lowering* cause for highs, a *cause* for lows.
   - **Correction bolus** — same model, flagged distinctly (mirrors existing `ConfounderType.correctionBolus`).
   - **Basal** — `ExponentialInsulinModel.basal(diaMinutes:)`.
   - **Exercise** — `[startTime, endTime + recovery tail]`; lowering influence that can persist post-session.
   - **Stress proxy** — sustained heart-rate elevation over baseline from `heartRateSeries` during the run-up (raising influence). Clearly labelled low-confidence.

3. **Ranking.** Score each candidate by **temporal alignment** (does its peak-influence window coincide with the excursion's rise/fall?) × **physiological plausibility** (magnitude vs. the clinical curves) × **direction match** (does its expected effect match the excursion direction?). Emit a ranked `[PatternCause]` with a human-readable reason ("Meal 2h10m ago, 60g carbs — peak absorption coincides with the rise") and a confidence tier. **Ranking weights and the absorption/onset curve shapes must cite Part 3 materials** (see input B) — until those land, ship with the existing IOB model + conservative defaults and mark the weights `// TODO(DMNC-792 Part 3): calibrate against <course figure>`.

4. **Output model.**
   ```
   struct PatternCause: Identifiable {
       let id: UUID
       let eventType: EventMarkerType        // meal / bolus / correction / basal / exercise
       let sourceID: UUID                    // back-reference to the meal/insulin/exercise entry
       let timeBeforeExcursion: TimeInterval
       let direction: CauseDirection         // .raises / .lowers
       let confidence: CauseConfidence       // .high / .medium / .low(proxy)
       let reason: String
       let score: Double
   }
   struct PatternResult { let excursion: Excursion; let causes: [PatternCause] }
   ```

5. **Trigger model.** Compute **on demand** from the tap (not on every glucose reading) to avoid the per-reading cost the passive-badge option would incur. The middleware fetches any out-of-window historical glucose/events via GRDB, runs the pure `PatternFinder`, and dispatches `.setPatternResult(...)`. Honour the `appState == .active` load guard and the "reducer runs before middleware" ordering (CLAUDE.md gotchas).

### 2.4 UI

A results panel presented **the same way Meal Impact is** — through `SheetCoordinator` (the single presentation root; never a local `.sheet`). Add an `ActiveSheet.patternResult(Excursion)` case routed via `RootSheetContent.swift`. The panel reuses the visual language of `EntryGroupListOverlay`: a ranked list of cause rows (icon per `EventMarkerType`, reason subline, confidence chip), tappable through to the underlying meal/insulin/exercise detail. Exact layout follows the Figma frame (input C).

### 2.5 Files touched (Part 2)

- **New:** `Library/Content/PatternFinder.swift` (pure engine + `Excursion`, `PatternCause`, `PatternResult`, `CauseDirection`, `CauseConfidence`).
- **New:** `App/Modules/PatternFinder/PatternFinderMiddleware.swift` (trigger + historical fetch). Register in **both** middleware arrays in `App.swift` (device + simulator — CLAUDE.md).
- **New:** `App/Views/Overview/PatternResultView.swift` (results panel).
- **State (GRDB-style transient, no UserDefaults):** `patternResult: PatternResult?` in `Library/DirectState.swift` + `App/AppState.swift` (`= nil`) + `Library/DirectReducer.swift`; actions `.findPattern(at: Date)` / `.setPatternResult(PatternResult?)` in `Library/DirectAction.swift`.
- `App/Views/Overview/ChartView.swift` — extend the existing `.chartOverlay` `DragGesture` tap branch (currently clears selection on tap) to dispatch `.findPattern(at:)` when the tapped point sits in an excursion. Coordinate with the existing tap-to-pin behaviour so the two gestures don't fight (a long-press or a dedicated "investigate" affordance may be cleaner — confirm against Figma).
- `App/Views/SheetCoordinator.swift` + `App/Views/RootSheetContent.swift` — add the `patternResult` sheet case.
- Reuse (no change): `IOBCalculator.swift`, `MealOverlayLogic.swift`, `EventMarker.swift`.

### 2.6 Tests (Part 2)

- `PatternFinderTests` (Swift Testing): excursion snapping from a tap time; candidate enumeration windows; ranking ordering for canonical scenarios (meal-only high, exercise-induced low, correction-bolus-stacked low, basal drift). Pure-function tests, UserDefaults-isolated via `makeTestDefaults()`.
- Direction-match tests (a bolus ranks as a *cause* of a low and a *mitigator* of a high).
- Confidence tiering (HR/stress proxy always `.low`).
- New test file → manual `project.pbxproj` entry in `DOSBTSTests` group + `PBXSourcesBuildPhase` (CLAUDE.md — tests are not auto-synced).

## Cross-cutting: scope, sequencing, and recommendation

### Recommended split into child issues

DMNC-792 as written is an epic. Recommend (operator to create, or confirm I should):

- **792-A — Clinical references (Part 3).** Independent. Ships the folder, index, and cross-reference audit. Only blocker is materials handover (B). **Do this first** — it feeds Part 2's ranking.
- **792-B — Horizontal-bar overlay restructure (Part 1).** Gated on Figma frame (C) + transcription confirm (A). Overlay infrastructure + opt-in flag.
- **792-C — Pattern Finder (Part 2).** The big one. Depends on 792-A for ranking weights and benefits from 792-B's overlay surface for presenting results. Build the pure engine + tests first (no design dependency), then wire the UI once the frame lands.

### Suggested sequence

```
Input B (materials) ─▶ 792-A (clinical refs + audit) ─┐
                                                       ├─▶ 792-C engine ─▶ 792-C UI
Input C (Figma frame) ─▶ 792-B (overlay) ─────────────┘            ▲
Input A (transcription confirm) ─▶ scopes 792-B + names 792-C ─────┘
```

The **pure `PatternFinder` engine + its tests have no design or materials dependency** and can be built immediately as the critical-path de-risking step (ranking weights left as calibratable TODOs until B lands).

### Risks & mitigations

- **Tap-gesture collision (Part 2).** The chart's `.chartOverlay` drag already owns tap-to-pin. Adding tap-to-investigate risks ambiguity — mitigate with a distinct affordance (long-press, or an "investigate" toggle) confirmed against the Figma frame; pin `selectedSmoothSensorPoint` clearing behaviour in a test.
- **Overlay regressing the no-overflow invariant (Part 1).** The adaptive `chartHeight(available:)` + safe-area-inset layout is load-bearing (`swiftui-vstack-overflow-sinks-safeareainset`). Ship behind a flag; keep the stacked layout as default until the Figma frame is validated by screenshot.
- **Ranking credibility without clinical grounding (Part 2).** Shipping a cause-ranker that contradicts the course material would undermine trust. Mitigate by gating ranking-weight finalisation on Part 3 and labelling proxy causes (stress/HR) low-confidence.
- **Materials privacy/copyright (Part 3).** Confirm commit-ability; strip PII; `.gitignore` + reference if not redistributable.
- **Day/night boundary flips (cross-ref).** Excursion thresholds read the active alarm profile; a mid-excursion boundary flip is the accepted behaviour pinned in `BoundaryFlipBehaviorTests` / DMNC-895 — Part 2 inherits it, no new handling.
