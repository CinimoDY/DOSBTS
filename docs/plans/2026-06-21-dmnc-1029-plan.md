# fix: tab bar unselected item tint under iOS 26 Liquid Glass

## Summary

Unselected tab labels/icons render system white/gray instead of dim amber — the last "real white" left after the CGA pass (builds 99–101). The cause is that `ContentView.onAppear` tints the bar only through the **convenience** proxy `UITabBar.appearance().unselectedItemTintColor`, which the iOS 26 Liquid Glass tab bar ignores. The fix is to configure the **granular** per-state colors on the `UITabBarAppearance` object the code already builds — `stackedLayoutAppearance.normal.iconColor` + `.normal.titleTextAttributes[.foregroundColor]` (and the inline/compact layout variants) — which the Liquid Glass bar still honors. This is a small, low-risk change gated behind an implement-run-observe verification loop, because (per the related learning doc) iOS 26 glass tinting behavior is undocumented and was found empirically.

## Problem Frame

After the CGA "no real white" pass, every surface the app controls renders in phosphor amber on black — except the bottom tab bar. On iOS 26 the **selected** tab is correctly amber (it picks up the SwiftUI root `.tint(AmberTheme.amber)` in `App.swift:46` and the redundant `UITabBar.appearance().tintColor`), but the **unselected** tabs render the system secondary color (white/gray). The origin CGA scope deliberately left native tab-bar chrome untouched, so this was filed as a scoped follow-up: find a per-item tint that survives the glass capsule rather than fighting it.

### Current state (the relevant code)

`App/Views/ContentView.swift` — second `.onAppear` (lines ~145–167):

```swift
let appearance = UITabBarAppearance()
appearance.configureWithOpaqueBackground()
appearance.backgroundColor = .black

UITabBar.appearance().scrollEdgeAppearance = appearance
UITabBar.appearance().standardAppearance = appearance
UITabBar.appearance().unselectedItemTintColor = UIColor(AmberTheme.amberDark) // ← IGNORED under Liquid Glass
UITabBar.appearance().tintColor = UIColor(AmberTheme.amber)                    // ← selected (works)
```

The tabs themselves use the classic value-tagged API in `ContentView.body` (lines ~37–53):

```swift
TabView(selection: selectedView) {
    OverviewView().tabItem { Label("Glucose overview", systemImage: "waveform.path.ecg") }.tag(DirectConfig.overviewViewTag)
    ListsView().tabItem    { Label("Glucose list view", systemImage: "list.dash") }.tag(DirectConfig.listsViewTag)
    SettingsView().tabItem { Label("Settings view", systemImage: "gearshape") }.tag(DirectConfig.settingsViewTag)
    DigestView().tabItem   { Label("Daily digest", systemImage: "doc.text.magnifyingglass") }.tag(DirectConfig.digestViewTag)
}
```

### Root cause

`UITabBarAppearance` exposes per-layout, per-state item colors via three `UITabBarItemAppearance` properties — `stackedLayoutAppearance` (portrait iPhone, the one that matters here), `inlineLayoutAppearance`, and `compactInlineLayoutAppearance` — each with `.normal` / `.selected` sub-states carrying `iconColor` and `titleTextAttributes`. The code never touches these. It relies entirely on the top-level convenience `unselectedItemTintColor`, which is a legacy shortcut. Under the Liquid Glass tab bar that shortcut no longer drives unselected items, so they fall back to the system color. The granular `UITabBarItemAppearance` route is the API community reports as still effective on iOS 26 (you set both normal **and** selected states explicitly on the appearance object), and it is precisely the path this code is missing.

## Options Considered

**Option A — Granular `UITabBarItemAppearance` on the existing appearance object. ✅ Recommended.**
Build a `UITabBarItemAppearance`, set `.normal` (icon + title → `amberDark`) and `.selected` (icon + title → `amber`), assign it to all three layout-appearance slots of `appearance`, and re-assign `appearance` to `standardAppearance` + `scrollEdgeAppearance`. The most-specific UIKit path; matches what we already do for the nav bar; ~10 lines; reversible; testable if extracted to a pure factory. Risk: like all iOS 26 glass behavior it is undocumented, so it must be visually verified before we trust it (see Verification). This is the cheapest thing that is most likely to work, so it goes first.

**Option B — Migrate to the value-based `Tab(_:systemImage:value:)` API.**
The issue suggests "SwiftUI `Tab` styling" as an avenue. Investigated: the value-based `Tab` builder (iOS 18+) is a structural/selection API — it does **not** expose an unselected-item color modifier. SwiftUI's `.tint` only drives the selected/accent color; there is no first-party SwiftUI knob for the unselected tab color on any iOS version. So migrating to `Tab` would be a parallel refactor that does **not** fix this bug. Rejected for this issue (noted as possible separate cleanup; would also force threading the existing `Int` tags through `value:` + a `Hashable` selection).

**Option C — Opt out of the Liquid Glass treatment for the tab bar.**
Forcing the bar back to a non-glass material (e.g. disabling the glass effect) could make the convenience tint apply again, but it fights the platform exactly as the issue says not to, regresses the iOS 26 look the rest of the app embraces, and is a heavier change than A. Rejected unless A and the granular route both prove ignored.

**Option D — Accept the system unselected color (do nothing / document).**
The honest fallback if A is empirically ignored: Apple may intentionally lock the unselected color for legibility over glass. Keep only if A fails verification; would close the issue as "platform-constrained" with the learning doc updated. Not the goal, but the explicit escape hatch.

## Key Technical Decisions

- **KTD-1 — Fix via the granular appearance API, keep the convenience setters as belt-and-braces.** Add the `UITabBarItemAppearance` config to the existing `appearance` object. Leave `tintColor`/`unselectedItemTintColor` in place (harmless, and they remain the correct fallback on any non-glass rendering / older OS); add a comment explaining why both exist. Net diff stays tiny.
- **KTD-2 — Extract a pure factory for testability.** Move the appearance construction into a small app-only helper, e.g. `App/DesignSystem/DOSTabBarAppearance.swift` returning a fully-configured `UITabBarAppearance`. `ContentView.onAppear` then just assigns it. This makes the color→token mapping unit-assertable (the appearance proxy install itself is not), and keeps `onAppear` readable. New non-test file under `App/` auto-syncs via `fileSystemSynchronized` — no pbxproj edit.
- **KTD-3 — Set all three layout appearances, not just stacked.** iPhone portrait uses `stackedLayoutAppearance`, but configuring `inlineLayoutAppearance` + `compactInlineLayoutAppearance` identically costs nothing and avoids a white relapse in landscape/compact-width or on iPad-style layouts.
- **KTD-4 — Selected stays amber; verify no SwiftUI/UIKit tint conflict.** Setting `.selected` explicitly to `amber` must not regress the working selected state, and must coexist with the root `.tint(amber)`. Confirmed in the same visual pass.
- **KTD-5 — Empirical gate before trusting the fix.** The related learning doc states all three known iOS 26 glass theming behaviors were discovered by implement-run-observe, undocumented. Treat this the same way: the change is not "done" until a simulator screenshot shows amber unselected items.

## Implementation Plan

Single small unit; the work is mostly the verification loop.

1. **Add `App/DesignSystem/DOSTabBarAppearance.swift`** — a pure factory:
   ```swift
   import UIKit

   enum DOSTabBarAppearance {
       static func make() -> UITabBarAppearance {
           let appearance = UITabBarAppearance()
           appearance.configureWithOpaqueBackground()
           appearance.backgroundColor = .black

           let item = UITabBarItemAppearance()
           item.normal.iconColor = UIColor(AmberTheme.amberDark)
           item.normal.titleTextAttributes = [.foregroundColor: UIColor(AmberTheme.amberDark)]
           item.selected.iconColor = UIColor(AmberTheme.amber)
           item.selected.titleTextAttributes = [.foregroundColor: UIColor(AmberTheme.amber)]

           appearance.stackedLayoutAppearance = item
           appearance.inlineLayoutAppearance = item
           appearance.compactInlineLayoutAppearance = item
           return appearance
       }
   }
   ```
2. **Rewire `ContentView.onAppear`** to consume the factory:
   ```swift
   let appearance = DOSTabBarAppearance.make()
   UITabBar.appearance().standardAppearance = appearance
   UITabBar.appearance().scrollEdgeAppearance = appearance
   // Belt-and-braces for non-glass / older renderings; the granular
   // item appearance above is what the iOS 26 Liquid Glass bar honors.
   UITabBar.appearance().unselectedItemTintColor = UIColor(AmberTheme.amberDark)
   UITabBar.appearance().tintColor = UIColor(AmberTheme.amber)
   ```
   (Net change in `ContentView`: a few lines; the nav-bar appearance block is untouched.)
3. **Add a unit test** `DOSBTSTests/DOSTabBarAppearanceTests.swift` asserting the factory's normal/selected icon + title colors equal `UIColor(AmberTheme.amberDark)` / `UIColor(AmberTheme.amber)` for the stacked layout (guards against a future token swap silently un-theming the bar). **Tests are not auto-synced** — add the file to the `DOSBTSTests` group + `PBXSourcesBuildPhase` in `project.pbxproj` (per CLAUDE.md).
4. **CHANGELOG** — at implementation time (not in this planning PR), add under `## [Unreleased]` → `Fixed`: "Tab bar — unselected tab labels/icons now render dim amber instead of system white under iOS 26 Liquid Glass — DMNC-1029".

## Verification (the gate)

This is the load-bearing step — the appearance-proxy install is the kind of thing that compiles green and renders wrong.

1. Build to simulator: `xcodebuild -project DOSBTS.xcodeproj -scheme DOSBTSApp -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=26.5' -configuration Debug build`.
2. Launch, screenshot the tab bar. **Pass:** the three unselected tabs render `amberDark` (#9a5700) icons + labels; the selected tab is full `amber` (#ffb000). **Fail:** any unselected item still white/gray.
3. Switch tabs and re-screenshot to confirm the selected/unselected swap holds (selected never goes dim, unselected never goes white).
4. If **fail:** the granular route is also ignored → fall back to Option C (de-glass the bar) or Option D (accept + document); update the learning doc either way.
5. Run the unit test (Cmd+U) — confirms the token mapping; it does not prove the on-screen result (that's step 2).

## Accessibility note (flag, not a blocker)

`amberDark` (#9a5700) measures ~3.74:1 on black — below the 4.5:1 WCAG AA text floor. The HIG/WWDC26 pass (DMNC, `2026-06-11-001` plan, KTD-2) deliberately moved *informational captions* off `amberDark` to `amber` for exactly this reason, while keeping `amberDark` for dimmed/secondary roles. An **unselected tab label is a legitimate dimmed/secondary affordance** (the system's own unselected gray is similarly low-contrast), so `amberDark` is defensible here and preserves the selected-vs-unselected contrast that signals state. Decision to confirm during review: keep `amberDark`, or use a brighter dim-amber / `amber` at reduced opacity if the unselected labels read as too dim in the screenshot. Either way the token stays in `AmberTheme` — no raw hex.

## Risks & Mitigations

- **Granular API also ignored by glass** → low-cost to discover (one build); fallbacks B/C/D documented above.
- **Selected state regression** from explicitly setting `.selected` → caught in Verification step 3.
- **Landscape/compact relapse** → mitigated by KTD-3 (all three layout appearances).
- **Token drift later** → unit test pins the mapping.

## Out of Scope

- Value-based `Tab` API migration (Option B) — does not fix this; possible separate cleanup.
- `tabBarMinimizeBehavior` / `tabViewBottomAccessory` — unrelated; the persistent INSULIN/MEAL bar already uses the `safeAreaInset` fallback (KTD-3 of the HIG plan).
- Any nav-bar / title styling (already handled by `dosNavigationTitle`).
